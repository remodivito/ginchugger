# Tough eval: seeded defects on a real agreement

This folder holds GinBench, the project's benchmark (decision 194). It keeps the name `tough-eval/` until the next benchmark version, because the frozen benchmark's file hashes are keyed on its paths. This page describes the first version (v1); GinBench v2 is in `BENCHMARK-V2.md` and its results in `v2/RESULTS-2026-10-17.md`.

Built 9 October 2026 because the four development tasks are near the ceiling (latest single-call runs: 151 of 161 criteria) and their judge scores recall only, so they cannot separate review architectures or see false findings.

## What it is

- **Agreement:** Common Paper Cloud Service Agreement v2.1 Standard Terms (CC BY 4.0; `sources/ATTRIBUTION.md`), verbatim with its published section numbering written into the text, behind a filled-in Key Terms block written for this suite. 145 paragraphs, about 35,700 characters, with real cross-references ("Except as provided in Section 8.4…") and a definitions section.
- **Position:** we are the Customer reviewing the Provider's paper. `playbook.json` holds 19 customer-side rules (caps, indemnity, data use, AI training, confidentiality, suspension, payment, renewal, termination, deletion, warranty, amendments, assignment, law, publicity, audit). Its preferred positions match the clean agreement, so a correct review of the clean copy raises nothing.
- **Mode:** third-party review with no baseline. The reviewer is not told what changed; it has to find each deviation by reading the whole agreement against the playbook. This is the hard condition.
- **Variants (37):** the clean agreement (`C00`); 27 single planted deviations (`P01`–`P27`): 5 easy (explicit values in the Key Terms), 13 medium (wording in the operative terms), 9 hard (cross-clause, in definitions, deletions that leave fluent text, a new clause inserted where no rule's natural home is); 6 benign edits that favour us or are neutral (`D01`–`D06`), which must not be flagged; and 3 variants with four plants each (`M1`–`M3`) to test whether findings survive dilution. The full list, with targets and the rules a correct review cites, is in `build.mjs` and `manifest.json`.

## Scoring (deterministic, no judge)

- A **flag** is a finding with status `attention` and any decision other than `accept`.
- A plant is **located** if a flag sits on a planted paragraph (by paragraph id, or a verified quote from it), and **caught** (headline) if that flag also cites one of the plant's playbook rules.
- A **false alarm** is a flag citing a playbook rule on a paragraph with no planted deviation. Flags on benign edits are reported separately (`benignFlagged`).
- With several runs, `score.mjs` prints a plant-by-run matrix and counts items every run catches, no run catches, and the discriminating ones in between.

## Running

Unattended: `node run-plan.mjs` runs every step in `plan.json` in order (bundle calibration, a first Opus 5.5 run, the controls, the two decomposed arms, then three repeats each of Opus 5.5 and both arms, one run of each arm without its consolidator, and three repeats each of Sonnet 5.5 and Opus 5, all on the development split), retries failed reviews after a wait (`--wait-minutes 30 --retries 6`, for the usage limit), skips finished steps when restarted, and ends with `score.mjs` and `compare.mjs`. A log goes to `run-plan.log`. `--dry-run` prints the commands. Rename a step to match a run you already have and it is reused.

Decomposed arms (decision 141): `--arm decomposed|decomposed-raw|decomposed-agent|decomposed-agent-raw` on `run.mjs`, or `"arm"` on a plan step. Each review then runs up to `REVIEW_CONCURRENCY` (default 4) rule workers at once, so keep `--concurrency` at 2. The result keeps the call count, tokens, cost, wall-clock, time to first memo and the consolidator's disposition table; the memos are under `traces/<variant>/memos/`.

Also: `node build-bundle.mjs` (after `build.mjs`), `node selftest.mjs` (scorer check), `node compare.mjs <runDir> ...` (repeats and paired comparison), `--control <name>` on `run.mjs`.

```
node tough-eval/build.mjs                       # rebuild variants and manifest (no model calls)
node tough-eval/run.mjs --name opus55-medium --model claude-opus-5-5 --effort medium --concurrency 3   # from a signed-in terminal
node tough-eval/score.mjs tough-eval/runs/<run> [<run> ...]
```

`run.mjs --demo` runs the v1 rule engine (`baselines/local-rules.mjs`, the product's former Sample mode; no model) as a floor. `--arm` runs the decomposed and agent arms (`arms/review-decomposed.mjs`, eval only). Their tests: `node --test tough-eval/arms/*.test.mjs tough-eval/baselines/*.test.mjs`. Each run writes a manifest with the hashes of the variants, playbook and review prompt before any review starts; run directories are never overwritten (and are not committed: `runs/` is ignored; results that matter are recorded in `../results-ledger.md`).

## Trust checks (10 Oct)

Before any score decides a design question, the eval has to show it can see differences and that a difference is not noise. Four checks, all in this folder:

1. **The scorer is checked against answers known in advance** (`node selftest.mjs`, no model calls). A perfect synthetic reviewer must score 100% caught and fixed with no false alarms; a silent one 0%; one that flags everything must catch everything but fail every agreement; one that cites the wrong rule must be "located" but not "caught"; and one that restates the planted wording must never count as a fix. The last two caught nothing wrong today, but they are what would catch a fix check that accepts the planted text, or a "caught" that ignores the rule.
2. **Deliberately worse configurations must score lower** (`run.mjs --control <name>`, `controls.mjs`): `half-document` (reviewer sees only the first half), `titles-only` (rules without guidance or tiers), `scrambled-ids` (each rule's guidance under a neighbour's id), plus Sample mode (`--demo`) and low effort (`--effort low`). If the eval does not rank these below the real configuration on the measure each one names, it cannot see that kind of difference.
3. **Repeats, with the noise measured** (`compare.mjs`). Each configuration is run three times. Reports mean ± standard deviation, pass^k (fixed in every run) and pass@k, and a paired comparison against a reference: per agreement, bootstrapped over agreements (plants in a markup are not independent), 95% interval. A difference counts only if the interval excludes zero and it is larger than the reference's run-to-run spread. On synthetic runs (`selftest.mjs --keep <dir>`), 3 runs × 34 development agreements give an interval of about ±7 points on "fixed": smaller differences cannot be claimed.
4. **A held-out split** (`split.json`, frozen): 15 of 49 variants (a third of the single plants, benign edits and markups, chosen by hash) are run but not scored until the final comparison (`compare.mjs --split heldout --final`). Held-out plants also appear inside development markups, so this guards against tuning to particular agreements, not to particular plant types.

Scorer additions: **all-pass** per agreement (every deviation caught and fixed, no false alarm, no benign edit flagged) and **surgical** fixes (no more than 5 words changed beyond what undoing the plant needs, word-level diff against the clean agreement).

Since 14 October (decision 148) all-pass is also **hallucination-gated**: a flag whose evidence quote is not found in the agreement, or which cites a playbook entry that does not exist, fails the agreement. These are the hallucinations this task can detect exactly, without a judge; misstatements inside a finding's reasoning are not checked by the scorer and are sampled by hand in the error analysis (`allPassUngated` keeps the old figure; `hallucinated` is the share of usable reviews with either kind). And a **failed review** (malformed output, provider error) now counts as an agreement in which nothing was found, rather than being left out: every deviation missed, all-pass false. `reliability` is usable reviews over attempted. `compare.mjs` adds the worst run's all-pass beside the mean. Scores published before 14 October excluded failed reviews; the Claude runs had none, so their figures are unchanged, while the open-model figures fall.

First control result: Sample mode catches 0% (its rules are written for NDAs), so it sits at the floor as it should.

## The long bundle (10 Oct, `build-bundle.mjs`)

Real deals arrive as an agreement plus annexes, and length is where a single review call is most likely to thin its attention per rule, so it is the one place a per-rule design has a real reason to help. The bundle is the agreement followed by a Data Processing Agreement and a Service Level Agreement (Common Paper DPA v1.1 and SLA v2.0 standard terms, CC BY 4.0, with filled-in cover terms written for this suite): 263 paragraphs, 62,000 characters, 1.7 times the agreement alone. It is reviewed against `playbook-bundle.json`: the agreement's 19 rules unchanged plus 8 for the annexes (C-20 to C-27: breach notification, subprocessors, subprocessor liability, audit, return and deletion, DPA liability and precedence, service levels, service-level remedies), written so the clean bundle meets them.

28 variants: the clean bundle (`B00`); 11 annex deviations (`BA28`–`BA38`, including cross-document ones: a DPA cap of 3 months' fees that undercuts the agreement's 3x privacy cap, SLA credits made the exclusive remedy for any performance failure, and a "Security Incident" definition narrowed to confirmed breaches); 4 harmless annex edits (`BD07`–`BD10`); 8 **length-paired** agreement plants (`BL01`…, the same plant as in the short agreement, now inside the bundle, so short and long can be compared plant for plant: `lengthPaired` in `score.json`); and 4 long markups (`BK2`–`BK6`: a development markup plus two annex deviations and one harmless annex edit). Agreement variants keep their 19-rule playbook, so earlier runs stay comparable. Run it with `run.mjs --variants bundle`; `--variants agreement` runs only the original suite. Split version 2 holds out 9 of the 27 bundle variants by the same rule.

Not yet calibrated: the clean bundle must raise no rule-citing flag with a real model before the bundle's results are believed (the agreement needed two playbook revisions for this). The length-paired comparison is confounded slightly by the longer playbook (27 rules against 19).

## What it does not establish

Synthetic positions and synthetic plants, written by Claude Opus 5.5 in this project's coding sessions on 9–10 October at the user's direction (corrected 15 October: this line said "the same person"), with no lawyer review. Opus also wrote the fix checks, and the clean bundle was calibrated until Opus raised no flag on it; Opus is one of the models under test. See `../benchmark-self-bias-research.md` and the v2 design in `BENCHMARK-V2.md`. One agreement, one playbook, one side. The plants were written knowing the playbook (as a counterparty's drafter would know market positions), but the playbook was not written against any model's output except for the calibration below. The suite measures finding deviations and avoiding false alarms; it does not score the quality of proposed wording.

## Calibration log

- **v0 → v1 (9 Oct).** One Haiku 5.5 smoke run (clean copy and P01). It caught P01 but raised 11 rule-citing flags on the clean copy. Causes on our side, fixed without touching any plant: (1) the importer drops Word's automatic numbering, so section numbers and list letters were missing while the text cross-refers to "Section 8.1(a)"; the published numbering is now written into the text; (2) the Key Terms omitted Variables the standard terms use (Additional Warranties, Notice Address, DPA, Use Limitations, currency) and phrased Increased Claims ambiguously; (3) the playbook was stricter than the clean agreement on ten points (e.g. the Provider's IP-remedy termination with refund, injunctions in any court, ML within third-party components of the Product); acceptable positions now say so explicitly (playbook version 2).
- **v1 result (9 Oct; Sonnet 5.5 and Opus 5.5, medium, 37 variants each).** On single plants both caught 100% of valid plants (easy, medium and hard alike), so single-plant recall does not discriminate. Item analysis found three items both models "missed", all faults in the eval: **P17** was invalid (deleting confidentiality from the damages-waiver exceptions changed nothing, because confidentiality breaches were still Increased Claims, which are exempt anyway); **P20** was ambiguous (removing the express inclusion left customer data inside limb (b) of the definition, and both models said so); and the four-plant variant **M2** contained P20. Both are rewritten in v2 (P17 now changes both places; P20 excludes Customer Content in terms). Opus also exposed a playbook fault (the rule promised a refund on termination for the Provider's breach, which the clean agreement does not give; and the export-controls termination was not clearly accepted): playbook version 3. What did discriminate: false alarms (Sonnet 1.18 per agreement, Opus 0.29).
- **Fix scoring.** First version required the original wording back verbatim ("restored": Sonnet 69%, Opus 84%), which looked like a quality gap. Reading the misses showed paraphrases that restore the protection and fixes landing on an acceptable position (60 days' notice; a 2x increased cap). Now each plant has a compliance check written from the playbook's acceptable tier (`fix` in `build.mjs`); on that measure Sonnet fixed 100% and Opus 97% of what they caught. Verbatim restoration is still reported as `restored`, for information only.
- **v2 (9 Oct).** Twelve realistic markups (`K01`–`K12`): each carries seven deviations and two benign edits together, assigned round robin from a seeded shuffle so each deviation appears two to four times in different company. Gap: P14 never fits beside the others (it shares a paragraph with the P24 insertion) and does not appear in any markup.
- **v2 partial result (9 Oct, interrupted).** Scored markups so far (Sonnet 8 of 15, Opus 5 of 15; the rest failed when the usage limit was reached): both caught every deviation in every markup (37 of 37 items), Sonnet's fixes complied 94%, Opus 100%; no false alarms and no benign edits flagged. Seven changes at once did not stress either model. Next lever: plants that are wrong only in combination with another clause (e.g. a definition change that silently widens a carve-out elsewhere), near-threshold edits on both sides of the playbook line, and a longer bundle (agreement plus DPA plus SLA). Re-run the failed variants with `run.mjs --resume <runDir>`.
- **Bundle calibration (10 Oct, Opus 5.5 medium, clean bundle `B00`).** Five rounds, each fixing only a fault in what we built, never silencing a flag because it was inconvenient. (1) The DPA promised audit reports "against the standards defined in the Security Policy", but our cover terms named no standard: the DPA cover now names SOC 2 Type II, an option on Common Paper's own cover page. (2) DPA §2.3 lets the Provider change the processing details, including purpose and special category data, by notice alone; a customer's lawyer would not accept it, so the negotiated copy removes that sentence (`SOURCE_EDITS` in `build-bundle.mjs`; a playbook carve-out was tried first and rightly still flagged). (3) The EEA SCCs must be governed by an EU member state's law: C-17 in `playbook-bundle.json` now says Irish law for the SCCs is acceptable. (4) Our SLA cover kept both of Common Paper's scheduled-downtime options, where the template says to choose one, which left unlimited maintenance on 48 hours' notice: only the Sunday window remains. (5) Two further clean runs: no flags. Each round raised a different single point, so clean-copy false alarms on the bundle are noisy; the controls and repeats measure that floor.
